# SmartAccess 产品需求文档（PRD）

## 1. 文档说明

- 产品名称：`SmartAccess`
- 文档类型：产品需求文档（PRD）
- 当前阶段：`MVP -> V1` 基线规划，v2 断代简化重构
- 主形态：`PyQt` 桌面端 + UI 自动化 + OCR 观测 + SpecLabOS/FastAPI 对接
- 部署约束：实验室内网优先，可选外部模型，可本地替代

## 2. 产品概述

SmartAccess 是一个面向实验室科学仪器上位机软件的非侵入式智能接入层。它的目标不是替代仪器原生控制软件，而是在不强依赖厂商 SDK/API 的前提下，用 AI 交互、UI 自动化和 OCR 观测，把实验操作和状态采集标准化，并将实验数据、过程日志、异常信息和标准工作流模板统一接入 SpecLabOS。

v2 主模型收敛为“锚点 -> 工作流 -> 执行”：锚点是可操作区域，每个锚点最多绑定一个可选 OCR 观测区域；步骤执行动作后，有预期 OCR 就轮询判断，没有观测就等待默认秒数。

## 3. 背景与问题

当前实验室的自动化和数字化建设常见以下问题：

- 仪器品牌和上位机软件差异大，统一接入难。
- 现有自动化多是单机脚本或人工 SOP，缺少标准工作流抽象。
- 实验过程中的关键状态依赖人工观察，难以实时记录与回放。
- 数据上传平台需要人工录入，实验参数与结果的一致性差。
- 出现执行异常时缺乏统一的告警、重试和恢复策略。
- 已验证的实验流程难以沉淀为可版本化、可回拉的模板资产。
- 早期模型中的多层绑定、手工结果声明、复杂判断表达和多模式识别对普通用户过重，容易造成配置重复和概念混淆。

SmartAccess 的任务是构建一个通用的实验执行与观测中间层，让更多仪器以较低改造成本接入标准化实验管理体系，并把标准工作流沉淀到 SpecLabOS 模板中心。

## 4. 目标与非目标

### 4.1 产品目标

- 让实验室可以在不修改上位机核心软件的前提下接入 SpecLabOS。
- 用 AI 引导非程序员配置锚点集和线性实验工作流。
- 把 UI 操作、OCR 观测、实验日志和平台回传串成闭环。
- 让新仪器接入具备模板化、可复用、可回归的交付方式。
- 让标准化工作流可以发布到 SpecLabOS 模板中心，并支持按模板 ID 和版本再次下发执行。
- 提供统一工作台，使锚点、工作流、模板/平台和执行在同一产品框架内完成。

### 4.2 非目标

- 不直接替代厂商的仪器控制逻辑、驱动或安全联锁系统。
- 不承诺在首版中支持所有品牌和全自动流程。
- 不在没有审计和安全约束的前提下执行高风险物理动作。
- 不在 v2 支持复杂流程控制、多模式识别或用户手工声明结果字段。
- 不把平台旧字段名反向引入主契约；需要兼容时由平台适配器映射。

## 5. 目标用户

### 5.1 一线科研人员

- 诉求：快速把实验步骤标准化、减少重复操作、降低手工录入。
- 成功标准：可以通过锚点选择和单 prompt 生成流程，复用模板并查看运行结果。

### 5.2 实验室管理人员

- 诉求：统一记录实验过程、掌握运行状态、沉淀模板和数据资产。
- 成功标准：可查看任务状态、日志、异常、模板版本和 trace 事实回传结果。

### 5.3 平台/自动化工程师

- 诉求：快速接入新仪器、维护平台字段映射、建立回归评测。
- 成功标准：新增一个仪器时有明确契约、模板、模板发布机制和验收路径。

## 6. 典型使用场景

### 场景 1：首次创建锚点集

用户打开仪器上位机，SmartAccess 扫描窗口并截图。用户在锚点页框选动作区域和可选 OCR 观测区域，保存为 `anchors.yaml`。

### 场景 2：通过自然语言生成实验工作流

用户选择锚点集，输入实验目标和步骤。AI Agent 结合已保存锚点、模板和已批准 memory/skill 生成简化 `workflow.yaml` 草稿。

### 场景 3：标准工作流发布到 SpecLabOS 模板中心

用户完成标准化检查后，将简化工作流发布到 SpecLabOS。平台保存模板 ID、版本、适用锚点集、发布时间和来源，用于备份、审计和后续下发。

### 场景 4：SpecLabOS 按模板版本下发任务

SpecLabOS 向 SmartAccess 下发包含 `template_id + template_version` 的任务。SmartAccess 拉取模板内容、绑定本地锚点集并启动执行。

### 场景 5：实验运行中的 OCR 观测与执行页监控

SmartAccess 每步执行锚点动作；如果步骤带 `expected_text` 或 `match_mode == not_empty`，就对该锚点 `observe_region` 做 OCR 轮询。执行页展示当前步骤、期望 OCR、实际 OCR、最新截图和日志。

运行监控页必须保证长步骤、长 OCR 文本和错误详情可滚动查看；截图、trace、workflow 和 anchors 等产物引用应以可点击链接展示，同时保留可复制路径。

### 场景 6：异常中断后的恢复

当发现窗口失焦、锚点缺失、OCR 超时或平台同步失败时，系统进入受控异常态，按恢复策略重试、等待人工确认或终止运行。

### 场景 7：实验数据、日志和模板复用闭环

SmartAccess 将阶段状态、步骤 OCR 事实、日志和关键截图上传至 SpecLabOS，并保留本地模板草稿、发布态和最近执行态，便于后续分析、审计、模板回滚和复用。

### 场景 8：能力示例验收

工程师可使用受版本控制的串口调试助手 UDP 示例和 Windows 计算器 OCR 示例验证系统能力。串口示例证明 UDP 服务打开、消息发送和日志 OCR；计算器示例执行 `12+34` 并用 OCR 证明结果区包含 `46`。

## 7. 产品范围

### 7.1 MVP 范围

- 支持 Windows 上位机场景。
- 支持单窗口仪器软件的基础锚点配置和执行。
- 支持基于点击、双击、输入、快捷键、回车和固定等待的工作流执行。
- 支持动作后 OCR 轮询判断和无观测默认等待。
- 支持 `anchors.yaml`、`workflow.yaml`、`platform_adapter.yaml`、`run_trace.jsonl` 四类主契约。
- 支持任务配置下发、状态上报、日志上传和 trace 事实上传。
- 支持标准工作流发布到 SpecLabOS 模板中心，并按模板 ID + 版本回拉执行。
- 支持 `GET /health`、`POST /api/v1/experiment/trigger`、`POST /api/v1/experiment/execute`、`GET /api/v1/experiment/status` 四个设备侧 FastAPI 基线接口。
- 支持工作台四个一级页面：`锚点`、`工作流`、`模板/平台`、`执行`。
- 支持锚点 normalized region，在窗口尺寸变化时按当前窗口尺寸重新映射坐标。
- 支持本地日志、异常告警和人工确认恢复。

### 7.1.1 v2 简化范围

- **锚点配置唯一入口**：`anchors.yaml` 顶层为 `profile_id`、`window_signature`、`anchors[]`。
- **线性工作流**：步骤只包含 `anchor_id`、`action`、`value?`、`expected_text?`、`match_mode`、等待和确认字段。
- **OCR-only 观测**：本地 vision provider 只保留截图、裁剪、OCR 读取和文本匹配。
- **真实动作链路**：Win32 SendInput/SetCursorPos 驱动 click、type、hotkey、press_enter；双击用两个连续 click 步骤表达。
- **运行 trace 自动产出**：每步记录动作、等待策略、期望 OCR、实际 OCR、匹配结果、尝试次数、耗时、截图路径和错误详情。
- **AI 工作流生成单 prompt**：内部流程为 `prompt -> memory/skill/template 检索 -> step intent -> anchor resolver -> simplified workflow`。
- **模板/平台保留一级入口**：只发布、回拉和同步新简化 workflow。

### 7.2 V1 范围

- 增强多窗口、多页面切换。
- 支持 Linux 上位机场景。
- 支持模板市场、批量锚点集管理、角色权限细化。
- 支持更成熟的模板审核、发布审批和回滚治理。
- 在 v2 主模型稳定后，再评估分支、循环和更强状态识别能力。

### 7.3 暂不纳入范围

- 直接控制底层驱动或 PLC。
- 未经审批的全自动危险动作执行。
- 面向公网的多租户 SaaS 形态。
- 在 MVP 中支持完整模板直传执行。
- 用户自定义结果字段、复杂判断编辑器和多模式识别配置。

## 8. 核心功能需求

### 8.1 锚点配置

- 支持创建锚点集，包括窗口签名、动作区域、可选观测区域和动作列表。
- 支持窗口扫描、截图、画布框选和锚点表编辑。
- 支持同时保存像素坐标和 normalized 坐标。
- 支持为每个锚点设置 `supported_actions` 和 `default_wait_seconds`。
- 支持把原接入页中复杂类型说明、安全页、识别模式、基准配置、能力确认和 AI 接入建议移除。

### 8.2 AI 引导式工作流生成

- 支持自然语言描述实验步骤并生成工作流草稿。
- 支持选择当前锚点集作为工作流上下文。
- 支持单 prompt 输入、生成按钮和步骤表。
- 支持标准化检查：锚点集存在、步骤非空、锚点存在、动作在锚点能力内、有 OCR 预期时锚点必须有观测区域。
- 支持版本化保存和二次修改。
- 禁止 AI 输出复杂绑定、手工结果声明、复杂判断对象或多模式识别字段。

### 8.3 OCR 观测

- 支持对锚点 `observe_region` 截图、裁剪和 OCR 读取。
- 支持 `contains`、`equals`、`regex`、`not_empty`、`none` 文本匹配。
- 支持 OCR 超时失败、低置信提示和人工确认。
- 支持将实际 OCR 文本、命中结果和截图路径写入 trace。

### 8.4 自动化执行

- 支持 `click` 点击 `action_region` 中心；双击用两个连续 `click` 步骤表达。
- 支持 `type` / `hotkey` / `press_enter` 先聚焦该锚点再输入或按键。
- 支持执行前安全检查，例如窗口存在、锚点可定位、步骤需要人工确认。
- 支持开始、停止、取消和 OCR 轮询可中断。
- 支持基于模板 ID + 版本拉取到的工作流生成本地执行上下文。

### 8.5 平台通讯与适配

- 支持通过 FastAPI 与 SpecLabOS 交换任务、模板、状态、日志和 trace 事实。
- 支持平台字段映射和格式转换。
- 支持连接保活、失败重试和本地缓存。
- 支持本地字段 `anchor_profile`；如果平台需要旧字段名，由平台适配器映射。
- 支持任务下发与模板拉取分离，避免把任务队列接口与模板中心接口混为同一职责。

### 8.6 日志、监控与审计

- 记录每个步骤的输入、动作、OCR 观察、执行状态和产物链接。
- 执行页展示当前步骤、期望 OCR、实际 OCR、最新截图和日志。
- 步骤时间线和步骤审计需要支持长文本滚动、选择和换行；文件引用以超链接展示。
- 支持关键截图回溯、运行时间统计和异常告警。
- 支持实验过程追踪和平台侧审计。
- 支持记录模板发布、模板拉取、版本命中和执行来源。

### 8.7 模板复用与模板中心

- 支持工作流模板和平台映射模板。
- 支持模板版本管理、复用和差异说明。
- 支持模板查找、状态过滤、版本时间线、基础更新、增加、删除和回滚操作。
- 当前本地回滚语义为切换当前发布版本，不等同于完整文件历史恢复。
- 支持标准工作流发布时自动上传到 SpecLabOS 备份。
- 支持 SpecLabOS 作为中心模板库保存模板 ID、版本、适用锚点集、发布时间和来源。

### 8.8 异常告警与恢复

- 支持检测 OCR 失败、窗口异常、锚点缺失、回传失败、状态不收敛等异常。
- 支持重试、等待人工确认、终止运行三类恢复动作。
- 支持把异常上下文完整记录到 `run_trace.jsonl`。
- 支持区分模板拉取失败、模板版本不存在和执行链路失败三类平台相关异常。

### 8.9 工作台与界面框架

- `锚点`：窗口扫描、截图、画布、锚点表、action/observe 双区域保存。
- `工作流`：当前锚点集选择、单 prompt 输入、生成按钮、步骤表和标准化检查。
- `模板/平台`：模板列表、版本历史、发布/回拉、平台字段映射和 trace 同步状态。
- `执行`：开始/停止/取消、当前步骤、期望 OCR vs 实际 OCR、最新截图和日志。
- 移除早期引导页和概览页作为一级入口。
- 采用“左侧导航 + 中央主工作区 + 右侧上下文详情”的统一布局原则。

## 9. 关键流程与状态流转

### 9.1 工作流生命周期

`Draft -> Standardized -> Published -> Ready -> Running -> Blocked -> Completed/Failed -> Archived`

状态说明：

- `Draft`：刚生成或编辑中的草稿。
- `Standardized`：已通过锚点集、动作能力和 OCR 观测校验。
- `Published`：模板已上传至 SpecLabOS 模板中心并具备稳定模板标识与版本。
- `Ready`：前置运行条件满足，可提交运行。
- `Running`：正在执行自动化动作与 OCR 观测。
- `Blocked`：因异常暂停，等待恢复动作或人工确认。
- `Completed/Failed`：执行结束并完成本地记录。
- `Archived`：本次会话结束，仅保留记录和产物。

### 9.2 典型链路

1. 用户进入锚点页并保存 `anchors.yaml`。
2. 用户在工作流页选择锚点集，通过单 prompt 生成 `workflow.yaml`。
3. 工作流完成标准化检查后发布到 SpecLabOS 模板中心。
4. SpecLabOS 下发包含 `template_id + template_version` 的任务，SmartAccess 拉取模板内容。
5. 系统执行步骤并持续产出 `run_trace.jsonl`。
6. 平台同步阶段状态、步骤 OCR 事实、日志和截图引用。
7. 若异常发生，则依据恢复策略进入恢复链路。

## 10. 非功能需求

### 10.1 兼容性

- MVP 支持 Windows 上位机。
- V1 规划支持 Linux。
- 对仪器厂商不做强耦合要求，但要求可见 GUI 和基础输入能力。

### 10.2 安全性

- 默认只做非侵入式 UI 级操作，不改写仪器原生业务逻辑。
- 需要定义人工确认点。
- 高风险动作必须具备可审计和可中止机制。
- 模板发布和模板回滚需要记录操作人和版本说明。

### 10.3 可靠性

- OCR 轮询可超时、可中断、可记录失败事实。
- 平台断连时支持本地缓存和补传。
- 关键异常必须产生告警和上下文日志。
- 模板拉取失败时不应覆盖本地最近一次可执行模板副本。

### 10.4 可扩展性

- 新仪器接入应尽量依赖锚点契约和模板，而不是写死脚本。
- 动作原语和平台映射必须可增量扩展。
- 模板中心字段和版本语义必须支持后续扩展审批、审核和模板市场。

### 10.5 可追溯性

- 每次会话都有唯一标识。
- 每个步骤的动作、OCR 观测、结果、截图和异常有迹可循。
- 每次模板发布、拉取、执行都能追溯到模板 ID、版本和来源。

### 10.6 性能约束

- 常规截图与 OCR 不应显著阻塞执行链路。
- OCR 轮询间隔和超时应满足实验实际节拍要求。
- 平台回传失败时不应直接丢失本地执行记录。
- 模板拉取和状态轮询不应阻塞本地异常恢复链路。

## 11. 部署与权限

### 11.1 部署模式

- 优先采用实验室内网部署。
- 桌面端与仪器上位机同网段或同机运行。
- AI 能力允许云端模型接入，但必须可切换到本地替代。
- FastAPI 服务可与桌面端同进程部署，也可作为本机局部服务暴露给 SpecLabOS。

### 11.2 权限边界

- 科研用户：创建工作流草稿、运行已授权模板、查看自己的日志和结果。
- 管理员：查看模板、异常、配置和模板发布记录。
- 工程师：维护锚点集、平台映射、模板版本和评测用例。

## 12. 成功指标

### 12.1 MVP 成功指标

- 至少可稳定接入 1 到 3 类典型仪器。
- 单个仪器的首次接入从人工脚本化降到锚点化流程。
- 实验关键状态可通过 OCR trace 自动回传平台。
- 标准工作流可发布到 SpecLabOS 并按模板 ID + 版本回拉执行。
- 执行异常具备标准化记录和恢复入口。

### 12.2 V1 成功指标

- 模板复用覆盖多类仪器场景。
- 接入效率、数据完整性和异常闭环能力显著提升。
- 平台可对接更复杂的任务编排和可视化监控。
- 模板治理支持更成熟的审核、回滚和权限控制。

## 13. 风险与待确认项

- SpecLabOS 的真实 API 契约尚未完全落库，需要后续对齐。
- OCR 在复杂 UI、低对比度界面中的稳定性需要专项验证。
- 不同仪器的权限与安全边界差异大，需要分级管控。
- Linux 场景的 UI 自动化技术选型需要在 V1 前确认。
- 模板版本一致性、发布冲突和回滚治理需要在实现阶段进一步细化。
